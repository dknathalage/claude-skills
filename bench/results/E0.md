## Verdict

**The swarm works headless, after five fixes.** On the fixed run, T1 and T2 ran in parallel on Haiku, each passed a Haiku check, then T3 ran, then integration, then an Opus review: 10/10 hidden tests, review 8/10, $0.98, 234 s. Haiku cost only $0.06 of that. Opus planning and orchestration dominate on a job this small.

Arms in the table:
- `claude-skills`: the swarm, working
- `superpowers`: the baseline
- `inline-opus`: what happened when the Workflow tool was missing and Opus built it alone
- `cs-autoblocked`, `cs-sensitive`: failed setups, kept as evidence

## Fixes E0 forced

1. The Homebrew CLI (2.1.181) cannot use Opus 5.5, so the runner uses the desktop app's bundled CLI (2.1.326).
2. Workflows are off in headless sessions, so the runner passes `enableWorkflows: true` (and `workflowSizeGuideline: large`) to every arm.
3. Auto mode's classifier returns "no verdict" on file writes inside workflow workers, which is a hard failure. Runs use `acceptEdits` with an explicit allowlist (`Workflow`, Bash for git/dotnet/node, read-only basics), the same for every arm.
4. Task branches `build/<topic>/<id>` cannot coexist with the feature branch `build/<topic>` in git, so they are now `swarm/<topic>/<id>`.
5. Work folders nested inside the loaded plugin's directory make every write "sensitive", so they moved to `~/.cache/claude-skills-bench/work`.

After the run, checkers that opened worktrees outside the project were refused and had to work around it. Checkers now get their own isolated worktree, like workers do.

## Early read (n=1, not a result)

On f-small, the swarm was 43% cheaper and 22% faster than superpowers, but slower and pricier than Opus alone. That is expected on a 3-task job. F-medium in E1 is where parallelism should pay.
